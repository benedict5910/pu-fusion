## OB1 – gearbox diagnosis

Protocol: leave one whole operating profile out (4 folds, 3 test recordings each); the test profile is
excluded from scaling, fitting and sensor-quality calibration. Models: motor-only, gearbox-only, early
fusion, equal late fusion, reliability-gated late fusion.

* **Reproduction from raw:** the frozen model on the 3 held-out recordings reproduces the stored fold
  exactly (160 metric cells, 0 confusion-matrix mismatches).
* **All four folds (stored), clean, window macro-F1 (per-profile min–max):** motor 0.542 (0.28–0.87),
  gearbox 0.593 (0.39–0.82), early 0.591 (0.29–0.95), equal late 0.565 (0.29–0.91), gated 0.565 (0.29–0.91).
  Gated: accuracy 0.565, false alarms 0.445, missed faults 0.254, recording-level macro-F1 0.579.
* No model is shown to be better than another; with 4 folds of 3 recordings no significance test is possible.
  Performance varies strongly between operating profiles.

## OB2 – gearbox sensor-fault detection and reliability-aware fusion

Sensors actually present: motor-side and gearbox 3-axis accelerometers (no current channel on this bench).
Evaluated the existing per-axis quality check and reliability-gated fusion on the held-out profile from raw
signals: 40 fault settings (7 families × severities × each sensor, plus both sensors), 177 windows each
(`results/final/gearbox/tables.md`).

| Scenario (held-out profile) | Flagged (corrupted sensor) | Motor only | Gearbox only | Early | Equal late | Gated | Gated coverage |
|---|---|---|---|---|---|---|---|
| Clean | 1 % / 1 % (false flags) | 0.874 | 0.817 | 0.955 | 0.909 | 0.909 | 100 % |
| Motor dropout | 100 % | 0.167 | 0.817 | 0.167 | 0.167 | 0.817 | 100 % |
| Gearbox dropout / stuck | 100 % | 0.874 | 0.167 | 0.167 | 0.167 | 0.874 | 100 % |
| Gearbox noise 0 dB | 100 % | 0.874 | 0.343 | 0.352 | 0.751 | 0.878 | 100 % |
| Gearbox clipping 0.05 | 100 % | 0.874 | 0.178 | 0.178 | 0.178 | 0.910 | 100 % |
| Gearbox spikes 100 /s | 100 % | 0.874 | 0.277 | 0.167 | 0.331 | 0.599 | 100 % |
| Gearbox gain ×2 | **1 %** | 0.874 | 0.545 | 0.920 | 0.633 | 0.633 | 100 % |
| Both noise 0 dB | 100 % / 100 % | 0.366 | 0.351 | 0.373 | 0.489 | 0.489 | 100 % |
| Both dropout or stuck | 100 % / 100 % | 0.167 | 0.167 | 0.167 | 0.17–0.26 | 0.000 | **0 %** (withheld) |

* Detection: every family is flagged in 100 % of windows on the corrupted sensor except **gain errors (1 %)**
  and mild 20 dB noise on the gearbox sensor (18 %). Over all four folds the clean false-flag rate on the motor
  sensor is 16 % (1 % on this profile).
* Fusion: a failed sensor is excluded and the surviving sensor carries the diagnosis; with both failed the
  diagnosis is withheld on every window while the other models keep guessing. A degraded-but-alive sensor is only
  down-weighted (it keeps 36–46 % of the weight), so under spikes gated (0.60) stays below the clean motor sensor alone (0.87), and an
  undetected gain error hurts it (0.63 vs early 0.92).
* Recovery: tested in the virtual testbed (below): weights return and diagnosis resumes on restoration.
* **Not done:** the corrected detector (v2) and skill-weighted fusion (v3_strength) from the bearing work were
  not ported: both must be fitted on training recordings, which are unavailable. So `v3_strength` still has no
  independent test.

## OB4 – simulation-based virtual testbed

`src/pufusion/testbed.py`, `scripts/run_virtual_testbed.py`. A scenario replays a real held-out recording,
injects a seeded sensor fault for chosen windows, and runs each window through the same chain as the dashboard:
feature extraction → sensor check → frozen diagnosis model → `HealthTracker` → `HealthStore` (SQLite) →
HTML / CSV reports. Operator acknowledgement is part of a scenario.

* 15 scenarios (7 bearing, 8 gearbox), 549 windows, 36 logged state-change events: **15/15 scenarios,
  148/148 checks passed**; a second run produced an identical result file.
* Checks per scenario: every window logged; exactly one event per state change; no diagnostic value stored
  while diagnosis is suspended; all sensors failed → diagnosis suspended (SENSOR_FAULT, or INSPECT kept if
  already latched); a single failed sensor gets weight 0 and diagnosis continues; INSPECT never drops straight
  to NORMAL; acknowledgement logged and never returns to NORMAL; diagnosis resumes on restoration.
* Dashboard: Live Diagnostics has two new sliders ("Fault active from / until window"), so one run shows fault
  onset and recovery; defaults reproduce the previous whole-run behaviour. Verified through the dashboard script:
  bearing both-sensor outage in windows 4–6 of 8 (alert shown, three windows without diagnosis, events
  WARNING → SENSOR_FAULT → INSPECT), gearbox motor dropout in windows 11–20 of 30 (weight 0 then restored).
* Behaviour the testbed exposed (not hidden): spikes on the motor sensor drive a *healthy* gearbox recording to
  INSPECT (a degraded sensor is down-weighted, not excluded); the healthy gearbox recording shows WARNING in 22 of
  59 clean windows; healthy bearing K004 sits in WARNING (known false-alarm issue).
